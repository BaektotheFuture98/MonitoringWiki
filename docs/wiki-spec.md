# MonitoringWiki 상세 명세

서버 구현 사양과 파일 형식 참고 자료입니다. 에이전트 행동 지침은 AGENTS.md를 참고합니다.

## 디렉터리

- `raw/YYYY-MM-DD/HHMMSS.txt`: 불변 원본. 수신 날짜(디렉터리)와 시각(파일명)으로만 명명하고, 같은 초에 겹치면 `HHMMSS-2.txt`처럼 순번을 붙입니다. 서버가 받은 비정형 텍스트를 형식 변환 없이 그대로 저장하며, 추가만 하고 수정·삭제하지 않습니다. **`raw/`는 git에 넣지 않습니다**(`.gitignore`). 개인정보가 git 이력과 원격 저장소에 남지 않게 하기 위함이며, 백업은 따로 합니다. 리소스(`query | master | data | slowlog`)는 파일명이 아니라 내용에서 판별하며, 한 파일에 여러 리소스가 섞일 수 있습니다.
- `wiki/index.md`: **통합 색인**. 패턴 1개당 1행(패턴, 요약, 리소스, 대표 시그니처, confidence, last_seen)과 인프라 링크가 있습니다.
- `wiki/log.md`: 시간순 작업 기록.
- `wiki/patterns/`: 장애 패턴 페이지. `wiki/infra/`: 클러스터 구성. `wiki/_template.md`: 패턴 템플릿.

## 패턴 페이지 형식

frontmatter 필수 필드: `id`, `summary`(증상과 원인을 담은 한 줄 요약, 색인의 요약 열에 그대로 옮겨 적음), `confidence`(low|medium|high), `resources`, `first_seen`, `last_seen`, `occurrences`, `sources`, `solution_origin`(report|human|claude-inferred|official-doc). `id`는 kebab-case이며 파일명과 같습니다.

본문 섹션 순서: `## 원인`, `## 증상`(리소스별), `## 해결방법`, `## 관련 패턴`.

증상에 관측이 없을 때는 이유를 구분해 적습니다: `미관측(수집 실패)`, `미관측(이벤트 없음)`(수집했으나 해당 이벤트가 없음), `미관측(입력 없음)`(해당 리소스가 입력에 없음), `미관측(로그 없음)`(작업자 메모만 있고 로그가 없음). 원인을 알 수 없으면 `## 원인`에 "미상"과 확인된 사실만 적습니다.

confidence 기준: 증거 리소스 1개·발생 1회 = low, 2개 이상 또는 3회 이상 = medium, 2개 이상이고 3회 이상 = high.

## 시그니처 정규화

로그 줄에서 타임스탬프→`<TS>`, IP→`<IP>`, 노드명→`<NODE>`, 인덱스명(날짜 접미사 포함)→`<INDEX>`, 나머지 숫자→`<N>`으로 치환한 문자열을 시그니처로 씁니다.

## Ingest (승인된 보고서 컴파일)

서버(PoC)는 보고서를 받는 즉시 아래 절차를 자동으로 수행합니다. 의미 판단(2~6단계)은 서버의 LLM이 컴파일 계획(JSON)으로 내고, 계획 검증과 파일 쓰기(7~8단계)는 서버 코드가 합니다(설계: `docs/superpowers/specs/2026-10-15-poc-auto-compile-api-design.md`). 서버가 위키의 유일한 쓰기 주체이므로, 담당자가 `wiki/`를 직접 고치거나 대화로 받은 보고서를 수동으로 컴파일할 때는 서버를 멈춘 뒤에 합니다.

1. 서버가 보고서를 `raw/`에 저장합니다(같은 내용이면 저장·컴파일하지 않음). 개인정보를 `<USER>`, `<IP>`, `<COMPANY>`, `<KEYWORD>`로 바꾼 텍스트만 LLM에 보냅니다. 컴파일에 실패한 보고서는 `WIKI_ROOT=<저장소> python server/scripts/pending.py`으로 확인하고 retry로 다시 처리합니다.
2. 텍스트를 읽고 부분별로 리소스(query/master/data/slowlog), 로그 원문 인용, 보고서의 결론·원인 판단·권장 조치, 도구 해석(요약·타임라인·상관분석 표), 구성 정보(노드 수·티어·버전 등 장애와 무관한 현재 상태)를 구분합니다. 리소스를 판별할 수 없는 부분은 임의로 배정하지 말고 "미분류"로 두고 보고합니다. 증거는 로그 원문 인용(타임스탬프가 붙은 로그 줄)만 씁니다.
3. 리소스별 이상 징후(WARN/ERROR, GC overhead, circuit breaker, 노드 이탈, slowlog 임계 초과, 쿼리 지연 등)를 추출해 시그니처로 만듭니다.
4. `wiki/index.md`를 읽고 기존 패턴과 의미가 같은지 판단해 매칭합니다.
   - 매칭: `occurrences`+1, `last_seen`, `sources` 갱신. 새 리소스 증거면 `증상`과 `resources`를 보강하고 `confidence`를 조정합니다. 보고서가 기존과 다른 원인·해결을 제시하면 덮어쓰지 않고 `(추가 보고서 <날짜>)`로 기존 내용과 나란히 기록합니다.
   - 불일치: `wiki/patterns/<id>.md`를 `wiki/_template.md` 형식으로 새로 만듭니다. `원인`은 보고서의 원인 판단·결론에서, `해결방법`은 권장 조치에서 옮기고 `solution_origin: report`로 둡니다.
5. 같은 incident의 여러 리소스 시그니처는 보고서가 연관을 제시하면 하나의 패턴으로 컴파일합니다. 보고서가 연관을 제시하지 않으면 패턴을 분리하고 각 `## 관련 패턴`에 "동시 관측, 연관 미확인"으로 서로 링크합니다.
6. 2단계에서 구분한 구성 정보는 `wiki/infra/`를 수정하지 않고, 인프라 페이지와 다르거나 새로운 것을 "인프라 갱신 후보"(`infra_candidates`)로 작업 결과에 포함합니다.
7. `wiki/index.md`(새 행 또는 갱신)와 `wiki/log.md`를 갱신합니다. 새 패턴에는 `summary`를 반드시 씁니다. `wiki/log.md`의 ingest 항목에는 처리한 raw 경로를 반드시 적습니다(컴파일 대기 목록 판별에 쓰임).
8. 쓰기 전에 `wiki/` 전체를 상태 폴더에 스냅샷으로 남깁니다(최근 20개). git 이력·커밋은 PoC 이후 `GitWikiStore`로 추가합니다.

## Lint 점검 항목

고아 페이지, 깨진 링크, 색인 누락, 색인 요약·시그니처가 페이지와 어긋나는지, 페이지의 원인·해결과 `sources` 보고서의 서술이 일치하는지, `wiki/infra/`에서 `as_of`가 90일 이상 지난 페이지와 노드명·IP 기재 여부, 중복 의심 패턴, confidence 대비 증거 부족, 옛 `미관측` 표기를 점검해 목록으로 보고하고 `wiki/log.md`에 기록합니다. 고치기 전에 사람에게 확인합니다.
